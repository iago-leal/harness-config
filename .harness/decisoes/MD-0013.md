# MD-0013 — Caminho do cache de sync centralizado em `layout.py` (saneamento do T7)

- **D:** O caminho do cache de sincronia ganha fonte única em `core/domain/layout.py`: nova constante `SYNC_CACHE_REL_PATH = ".harness/sync-cache.json"`, da qual `SYNC_CACHE_GITIGNORE_ENTRY` passa a derivar. Os três consumidores — a CLI (`main.py`, alerta passivo de versão), o `SessionCloseFlow` (`close_flow.py`, ofertas de encerramento) e o servidor MCP (`adapters/mcp/server.py`, tool `check_repository_sync`) — deixam de chumbar o literal e leem a constante. Bump 2.0.0 → 2.0.1 para que os projetos vendorados percebam o fix pelo alerta passivo.
- **PORQUÊ:** T7 (achado da reconciliação de 2026-07-05, `gaps.md#G-12`): o `server.py:42` gravava o cache em `.harness/sync_cache.json` (underscore), enquanto CLI e close_flow usavam `.harness/sync-cache.json` (hífen) — o único nome coberto pelo `.gitignore` que o `init` grava. Desde a feature 019, cujo pré-check de pendência deixou de mascarar `.harness/` inteiro, o cache do MCP seria oferecido para commit como se fosse trabalho real. A constante única elimina a classe do erro, não só a instância: um literal divergente futuro exigiria reintroduzir o chumbado à mão.
- **DESCARTADO:** (1) Apenas alinhar o literal do `server.py` aos demais — corrige a instância e preserva três cópias do mesmo string, o mesmo terreno onde o T7 nasceu. (2) Ler o caminho de `harness.toml` (`SyncSection`) — o cache é infraestrutura interna sem caso de uso para variar por projeto; configurável seria superfície nova sem demanda (YAGNI). (3) Migrar/apagar caches `sync_cache.json` órfãos nos projetos — arquivo de TTL efêmero e inócuo; a remoção em massa fora deste repo não compensa o risco (cf. cautela do `migrate` real).
